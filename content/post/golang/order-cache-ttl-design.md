在支付系统中，生成支付链接是一个常见的操作。如果用户频繁点击"支付"按钮，每次都调用支付平台 API 创建新订单，不仅浪费资源，还可能触发风控。所以我们通常会缓存支付链接。

但缓存时间设置多少才合理？这篇文章通过分析一个真实的代码片段，来讲解这背后的设计思路。

<!--more-->

## 问题代码

```go
ttl := (constants.OrderExpireTime - 30*time.Second).Seconds()
```

其中常量定义为：

```go
const OrderExpireTime = time.Minute * 10  // 10 分钟
```

## 缓存时间计算

让我们先算一下实际的 TTL：

- `OrderExpireTime` = 10 分钟
- `ttl` = 10 分钟 - 30 秒 = **9 分 30 秒**

这个设计看似简单，但背后有深层的考量。

## 为什么这个设计是合理的？

### 1. 与支付平台订单有效期同步

支付平台（微信、支付宝等）的订单有效期通常是 10 分钟。缓存时间略短于订单有效期，确保我们不会返回已过期的支付链接给用户。

### 2. 30 秒缓冲时间的作用

这是最关键的设计点。让我们看一个时间轴：

```
订单创建时间轴：

0 分钟 ────────────── 9 分 30 秒 ────── 10 分钟
  ↑                      ↑                  ↑
创建订单              缓存过期          订单过期
                  (缓存失效)
```

**缓存提前 30 秒过期的好处：**

- 如果用户在第 9 分 40 秒请求，缓存已失效，系统会创建新订单
- 避免了边界情况：如果缓存和订单同时过期，可能返回无效的支付链接
- 给系统留出了反应时间

### 3. 业务场景匹配

这个缓存主要用于：

- **防止重复下单**：用户快速重复点击（几秒内）时，返回同一支付链接
- **提升用户体验**：用户在 10 分钟内多次获取支付链接，无需重新创建
- **自动失效**：超过 10 分钟后，订单自动失效，需要重新下单

## 时间轴示例

假设用户的操作流程：

```
时间点          用户操作              系统行为
─────────────────────────────────────────────────
0 秒            点击支付              创建订单，缓存 9 分 30 秒
5 秒            再次点击支付          返回缓存的支付链接
9 分 20 秒      再次点击支付          返回缓存的支付链接
9 分 40 秒      再次点击支付          缓存已失效，创建新订单
10 分钟         用户未支付            原订单过期，需要重新下单
```

## 潜在的优化方案

虽然当前设计已经很合理，但根据不同的业务需求，可以考虑以下优化：

### 方案 1：更保守的缓存时间

```go
// 缓存 5 分钟，更频繁地检查订单状态
ttl := time.Minute * 5
```

**优点：**
- 减少返回过期订单的风险
- 更及时地反映订单状态变化

**缺点：**
- 用户在 5-10 分钟内重新请求会创建新订单
- 增加支付平台 API 调用次数

### 方案 2：动态调整缓存时间

```go
// 根据订单创建时间动态计算剩余有效期
remainingTime := constants.OrderExpireTime - time.Since(order.CreateTime)
if remainingTime > 30*time.Second {
    ttl := (remainingTime - 30*time.Second).Seconds()
} else {
    // 订单即将过期，不缓存
    ttl = 0
}
```

**优点：**
- 更精确地利用缓存时间
- 避免缓存已接近过期的订单

**缺点：**
- 逻辑更复杂
- 需要存储订单创建时间

### 方案 3：添加订单状态检查

```go
// 从缓存获取后，验证订单是否仍然有效
if cachedOrder != nil {
    // 检查订单是否已支付或已过期
    if order.Status == OrderStatusPaid || 
       time.Since(order.CreateTime) > OrderExpireTime {
        // 清除缓存，创建新订单
        cache.Delete(key)
    }
}
```

**优点：**
- 确保返回的订单总是有效的
- 及时清理无效缓存

**缺点：**
- 需要额外的数据库查询
- 增加系统复杂度

## 当前实现的优点总结

✅ **简单高效**：不需要额外的数据库查询  
✅ **用户体验好**：10 分钟内可以重复获取支付链接  
✅ **安全边界**：30 秒缓冲避免边界问题  
✅ **资源节约**：减少重复订单创建  
✅ **易于维护**：逻辑清晰，易于理解和修改  

## 何时需要修改这个设置？

| 场景 | 建议 |
|-----|------|
| 支付平台订单有效期不同 | 根据实际有效期调整 |
| 用户投诉频繁创建新订单 | 增加缓存时间 |
| 用户投诉收到过期支付链接 | 减少缓存时间 |
| 支付平台 API 调用有限制 | 增加缓存时间 |
| 需要更严格的订单管理 | 使用方案 2 或 3 |

## 总结

当前的 **9 分 30 秒缓存时间** 是一个经过深思熟虑的设计，它在以下方面取得了很好的平衡：

- 防止重复下单
- 提升用户体验
- 避免返回过期订单
- 与支付平台订单有效期同步

**30 秒的缓冲时间** 是这个设计的精妙之处，它给系统留出了反应时间，避免了边界情况。

除非有特殊的业务需求，否则不需要修改这个时间设置。但理解这个设计背后的思路，对于设计其他缓存策略也很有帮助。
